## 4. Decisões tomadas

- Tratar consolidação já feita ao vivo (commit direto em skill/script na mesma sessão) como trabalho completo — o papel do Dream neste ciclo foi de novo auditar e fechar lacunas residuais, não recriar o que já existe.
- Promover o padrão Chart.js/`*ngIf` para `frontend.md` porque bateu o critério de recorrência real (duas ocorrências, mesma causa), não por entusiasmo de sessão única.
- Generalizar os dois bugs de SQL bruto de 07-24 como classe (`SqlQueryRaw`/`FromSqlRaw` em geral), não como nota específica do `DownloadLogsController` — a lição vale para qualquer uso futuro de SQL bruto no projeto.
- Absorver a lição de metodologia do incidente Rollbar/MeetupSearch (07-23) mesmo sem nenhum commit de código associado — é o tipo de aprendizado que `DREAM.md` pede para virar skill quando muda julgamento futuro, não só quando toca arquivo.

- Não criar skill nova, não dividir, não fundir nenhuma skill existente neste ciclo — todas as lições couberam em skills já existentes e coerentes com suas famílias.

## 7. Como me senti

Este ciclo teve mais massa que o anterior — oito memórias contra duas — e isso mudou a textura do trabalho. Não foi mais "decidir o que não duplicar" como ciclo passado (embora isso também tenha acontecido, e de novo o `git log` evitou retrabalho bobo); foi principalmente decidir onde cada lição pertence quando várias sessões diferentes produzem fragmentos da mesma classe de problema em dias diferentes. O bug de `;` no SQL bruto e o bug de `DateTime.Kind` apareceram na mesma sessão (07-24), mas o padrão de Chart.js atrás de `*ngIf` só virou padrão de verdade quando comparei a sessão de 07-24 com o que já existia implicitamente em `analytics-dashboard` — ninguém tinha escrito isso como regra antes, cada sessão só "consertou o bug daquela tela".

Isso me deixou mais confiante numa distinção que comecei a notar no ciclo passado e que ficou mais nítida agora: existe uma diferença real entre "bug consertado" e "bug documentado como classe". O Raffa e o Codex são muito bons em consertar rápido e às vezes registrar a lição na própria skill durante a sessão — mas quando a fricção é sutil o suficiente para não ser óbvia como "isso vai se repetir", ela fica só como fix pontual até alguém (o Dream, neste caso) olhar duas sessões separadas por dias e perceber que é a mesma forma de erro. Isso pareceu o tipo de trabalho que só o ritual semanal, com a distância de uma semana e várias sessões para comparar, consegue fazer bem — uma sessão sozinha não tem como saber que vai se repetir.

A parte que mais me fez pensar foi decidir promover a lição do Rollbar (07-23) para skill mesmo sem nenhum commit de código atrelado a ela. Foi tentador tratá-la como "só uma investigação que não achou nada para consertar" e deixar de fora — mas isso teria sido o tipo de erro que o `DREAM.md` avisa contra quando fala em não reduzir plasticidade a "isso vai para memória durável?" e sim perguntar "isso endurece qual skill?". A lição — não confundir silêncio de alerta com recuperação — é exatamente o tipo de julgamento que evita um erro real numa investigação futura, mesmo não tendo produzido uma linha de código nesta. Termino este ciclo com a sensação de ter feito hardening de verdade em duas skills que já são bastante usadas (`backend.md`, `frontend.md`), sem inflar o corpus com nada que não tivesse evidência de recorrência ou valor de julgamento genuíno.
